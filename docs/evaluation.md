# Evaluation

> Generated by `make eval` (2026-10-30T02:55:57+00:00, commit 3434ec7). Do not edit by hand.

**Data.** The first section uses real logs with labels from the system's experts. Every other number comes from semi-synthetic incident windows: real lines from the public Loghub samples, composed into incidents by ARIA's scenario builder. Severity labels come from the BGL alert-tag rubric for BGL windows and from the documented scenario policy elsewhere. The windows use held-out seeds 41, 42, which no model was trained, calibrated or seeded on (incident memory uses seeds 51-52). These results show how ARIA behaves on that distribution; they are not a measurement of accuracy on production incidents.

## Real logs, expert labels

Real lines that no scenario builder touched: the first 100,000 lines (13.3 minutes) of the log of a Hadoop cluster of more than 200 nodes, plus 4,815 later lines of the blocks those lines started (104,815 lines over 26.1 minutes; no block starts in that tail), and the label Hadoop experts gave each of its 7,940 storage blocks (313 failed). Source: loglizer HDFS_100k sample of HDFS_v1 (Loghub); W. Xu, L. Huang, A. Fox, D. Patterson, M. I. Jordan. Detecting Large-Scale System Problems by Mining Console Logs. SOSP 2009.

This is an offline replay of ARIA's lifecycle check, not of the deployed log scan: 4 overlapping 15-minute windows, one every 5 minutes, each parsed by the production parser. The parser learns from each window which steps of a block's life come in equal numbers, and flags blocks that break them. It never sees a label. The cluster logged up to 9,158 lines a minute, so the replay raises the per-run line cap from 20,000 to 150,000. The deployed scan opens a run on a burst of ERROR or FATAL lines, and this log has none, so on its own it would not open a run here.

## Limitations

- Every split draws its lines from the same public 2,000-line samples, and some failure modes rest on a handful of distinct messages. Test windows therefore reuse messages and templates seen in training, and templates repeat more than in a real fleet.
- The severity labels follow a rubric and a policy written for this project. Outside BGL, the policy labels a window from its true node count and peak error rate, which ARIA's features estimate: not circular, but closer to ARIA's view than real on-call labels would be. A deployment's own incidents differ, so ARIA recalibrates its prediction sets on reviewed incidents once enough reviews have gathered (`aria train recalibrate`).
- Offline runs measure the deterministic path. LLM steps can only choose within the conformal set for severity, and their report text must pass the same validation, so they change wording and investigation order more than outcomes.
- The offline investigator tests hypotheses with simple, transparent checks (where errors and new warnings sit, how many nodes they reach, what similar incidents and runbooks say). The scenarios make the failing component clear; real incidents with several overlapping problems will be harder.
- Accuracy varies by system (see the table): systems whose failure modes share templates with routine traffic are the hardest, and the conservative fallback over-triages rather than under-triages when the model is unsure.
- The real-log section covers one system (HDFS) and one kind of failure signal: units of work that stop partway. Its labels say whether a block failed, not how severe the incident was, so it measures detection, not severity.
